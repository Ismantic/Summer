# 数据格式约定

预编码产物长什么样、特殊 token 各自什么含义、对话怎么打包成定长序列。
**这些约定改错了不会报错**,只会让训练悄悄学到别的东西 —— 所以单独成篇。

配方和超参在 `prepare/Makefile`,为什么这么设计在 `WHY.md`,这里只讲**格式**。

## 特殊 token

词表 81903 = 81899 个普通 piece + 4 个特殊,加上 piece 词表自带的 3 个。

| id | 名字 | 预训练里出现过? | 用途 |
|---|---|---|---|
| 0 | `<unk>` | — | 未知 |
| 1 | `<bos>` | **否** | 对话/序列开始 |
| 2 | `<eos>` | **是,约 0.094%** | 文档边界(**只用于预训练**) |
| 81899 | `<pad>` | 否 | 尾部填充 |
| 81900 | `<user>` | 否 | 用户段开始 |
| 81901 | `<assistant>` | 否 | 助手段开始 |
| 81902 | `<end>` | 否 | **回答结束**(专用停止符) |

> **81902 在词表里的字面名字是 `<system>`**,改名要重建分词器,不值得。
> `<end>` 是代码和文档里的名字,指的就是 81902。它在预训练里出现 **0 次**,
> 和新加一个 token 等效。

### `<eos>` 曾经身兼两职 —— 已修

预训练语料里每篇文档之间用 `<eos>` 分隔,实测占 0.094%(2M token 里 1927 次)
—— 也就是整个 S0 的 11.8B token 里出现过约 1100 万次,含义是「**一篇文档结束,
后面还有下一篇**」。

SFT 又拿同一个 token 表示「一次回答结束,该停了」。这两个含义是冲突的:
前者暗示「后面还有」,后者要求「到此为止」。而 12M token 的 SFT 要去覆盖
11.8B token 建立的先验,**差三个数量级**。

实测后果:SFT 之后贪心解码只有约 50-55% 的位置能正确停下。失败时模型 75%
的情况想输出 `\n`(预训练里「句号后接换行」的先验)。多训 3 倍、改用 best-fit
打包,各只带来 2-3 个百分点。

nanochat 没有这个问题,因为它用**专用的** `<|assistant_end|>`
(还有配对的 `<|user_start|>` / `<|user_end|>` / `<|assistant_start|>`),
这些 token 在它的预训练里没有旧含义要覆盖。

**已改成 nanochat 那样的分离方案**:回答结束用专用的 `<end>`(81902),
`<eos>` 只留给文档边界。两套格式现在完全不重叠:

```
token            预训练      对话(midtrain / SFT)
<eos>           0.0941%     0%        ← 只在预训练
<bos>           0%          0.20%     ← 只在对话
<user>          0%          0.44%
<assistant>     0%          0.25%
<end>           0%          0.25%
<pad>           0%          3.3%
```

nanochat 的预训练也只有一个特殊 token(`<|bos|>`,前置在每篇文档开头),对话
另有 `<|user_start|>` / `<|user_end|>` / `<|assistant_start|>` /
`<|assistant_end|>` 一整套 —— 文档边界和回答结束**永不共用同一个 token**。

系统消息怎么办:81902 腾给了 `<end>`,系统内容直接并进第一条用户消息,不引入
新标记。我们的对话数据里几乎没有 system 消息,代价很小。

## 预训练数据(`prepare/encode_corpus.py`)

```
<out>.s000.pt … .s0NN.pt     int32 [N, seq_len],mmap 读
<out>.mix.json               实际配比(planned vs actual)
```

- 文档之间用 `<eos>` 分隔,首尾相接后按 `seq_len` 切。**跨文档边界是有意的** ——
  预训练本来就要学「一篇结束后另一篇开始」。
- 没有 mask 文件,整段算 loss。
- 分 shard 是为了编码时能并行、断点续、单文件别太大。

## 对话数据(`prepare/chat.py`)

```
<out>.pt          int32 [N, seq_len]
<out>.mask.pt     uint8 同形状,1 = 这个位置要算 loss
<out>.mix.json    配比 + 被监督比例 + 尾部填充率
```

### 一条对话的 token 布局

```
[<bos>] [<user>] 用户内容 [<assistant>] 助手内容 [<end>]
mask:  0     0      0…0        0          1…1      1
```

有 system 消息时,系统内容并进第一条用户消息,不单独标记。

**只在助手回复和它后面的 `<end>` 上算 loss。** 用户那段不算 —— 否则模型会去学
「怎么生成问题」,那不是要的能力,还会稀释真正的监督信号。

midtrain 是例外:**整段算 loss**(mask 全 1)。那一步的目的是让模型见熟这个
格式,不是精调答案质量。

### 打包:best-fit,不切断,尾部补 pad

三条规则,缺一条就会出问题:

1. **每条序列里的对话都是完整的。** 早先的做法是首尾相接后按 `seq_len` 切,
   于是一条序列可能从半截对话开始 —— 那种上下文推理时永远不会出现。
2. **装不下就换新序列,尾部用 `<pad>` 补齐并 mask=0。** 不截断(截在助手回复
   中途会让模型学到「说到一半就停」),也不跨序列续写。
3. **用 best-fit 而不是 first-fit。** 每行反复挑「最大的还装得下的」那一段。
   实测填充率 25.6% → **7.6%**,被监督比例 65.6% → **81.6%** —— 差别是四分之
   一的算力在训 pad 还是在训数据。与 nanochat 的 `scripts/chat_sft.py` 一致。

### 尾部 padding 为什么是安全的

`src/model.py` 只做 `is_causal` 的因果注意力,**不接受 attention_mask**。
但 pad 在序列**末尾**:

```
真内容 … <pad> <pad> <pad>
  ↑         ↑
  看不见后面的 pad(因果)   看得见前面的真内容,但 mask=0 不算 loss
```

会算错的是**左侧或中间**填充,不是尾部。

### 超长对话:按轮次切段,不整条丢

一条多轮对话装不进 `seq_len` 时,**在轮次边界切成多段**,每段重新以 `<bos>`
开头。绝不截在一轮中间。

单轮本身就超长的(比如一问一答但答案很长),那一轮整个丢掉 —— 切不了。
这对 COIG-CQIA 影响很大:它是单轮长回答(考试题解析、知乎长答),中位数
**1126 token**,`seq_len` 1024 下只有 66% 能整条装下。

实测不同长度的保留率:

```
1024   66.0%  →  中文可得约  9M token
1536   81.8%  →           18M
2048   92.5%  →           26M
```

**决定保持 1024。** 预训练全程只见过 1024,位置 1024-2048 的 RoPE 从没训过;
用 2048 做 SFT 等于让模型在 12M token 里同时学「答得好」和「长位置怎么编码」。
而且瓶颈不在这 —— 对 Qwen3-0.6B-Base 的 MMLU 差 0.24,那是预训练 13B token
的问题。**这是已知限制,不是待修的 bug。**

## 两处踩过的坑

**估长度时用了会丢弃样本的函数。** 早先估 COIG-CQIA 的平均长度,用的是
「`encode_turns` 返回的 token 数 ÷ 条数」,但那个函数超长会返回空 —— 分母算了
全部、分子只算留下的短样本,越丢越显得平均短,估出 145 token/条(真实中位数
1126)。幸存者偏差。

**前缀长度写死成 1。** `encode_turns` 判断单轮是否超长时写的是
`len(turn_ids) + 1`,只给 `<bos>` 留一个位置;但带 system 的样本前缀有三个
token,于是会产出超过 `seq_len` 的段,一路漏到 `np.stack` 才报「shape 不一致」。
现在按实际前缀算,并在打包处加了断言 **让它在产生的地方就炸**。
