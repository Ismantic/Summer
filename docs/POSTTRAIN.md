# 后训练日志

Summer-0.5B 的 chat 线。每一版改了什么、量到了什么、结论是什么,按时间顺序记在这里。

- 数据格式和特殊 token 的**约定**在 [`DATA_FORMAT.md`](DATA_FORMAT.md)
- 底座训练和评测**结果**在 [`reports/summer-0.5b-pretrain.md`](reports/summer-0.5b-pretrain.md)
- 这里只记**每次改动**和它的效果。同一件事不重复写。

对齐基准是 **Summer = nanochat + 中文 + ReTok**,架构固定 Qwen3 ——
所以**偏离才需要理由**,对齐不需要。架构类的对齐项已关闭(见「对齐清单」)。

对照的是 nanochat 的 d20。按它的 depth 惯例(`hidden = depth×64`)换算到我们的
81903 词表,d20 = 596M / 嵌入 17.6%,和 Summer-0.5B 的 524M / 16.0% **同一鳞级**
—— 是公平对照,不是以小博大。官方 chatsft checkpoint 在手,加载方法见文末。

**两套设计,不要混着抄:**

```
         旧版(= d20,v1~v5 对照的)        新版(设计 B,上游 1ddaad1 之后)
预训练   连续流,无 BOS 对齐               BOS + best-fit
midtrain 连续流,全速 lr,整段算 loss       没有(混比并进 SFT)
SFT      best-fit,lr 2%,assistant-only   best-fit,**lr 0.8**,assistant-only
```

v1~v5 走的是旧版(两阶段);从预演起转向设计 B(单阶段)。

## v1:首版

midtrain 34.8M token,SFT 12M。回答结束**复用 `<eos>`**。

五项(似然协议):ARC-E 0.5324 / ARC-C 0.2474 / MMLU 0.2594 / GSM8K 0.0220 /
C-Eval 0.2608。**相对 S0 的 ARC-E 0.5564 掉了 0.024。**

问题:贪心解码停不下来。

## sft3:同样的数据多跑 3 倍

50.8% → 53.3%,**+2.5 点**。用来排除「训练量不够」这个解释 —— 排除掉了。

## v2:专用停止符 + best-fit + midtrain 加厚

三处改动:

1. **回答结束换成专用 `<end>`(81902)**,`<eos>` 只留给文档边界。
   `<eos>` 在预训练里占 0.094%(S0 全程约 1100 万次),含义是「一篇结束,
   **后面还有下一篇**」;拿它表示「到此为止」是直接冲突,而 12M 的 SFT
   要盖过 11.8B 的先验,差三个数量级。
2. **打包改 best-fit**,填充率 25.6% → 7.6%,被监督比例 65.6% → 81.6%。
3. **midtrain 从 34.8M 加到 103M**。

停止符探针:P 中位 0.325 → **0.595**,能停 50.8% → **65.0%**。
对照 sft3 的 +2.5 点,**瓶颈确实是含义冲突,不是训练量。**

但 ARC-E(似然)0.5324 → **0.4941**,继续掉。

### 这一版暴露的判据问题(三个,都是我的)

**判据错了不会报错,而且错出来的数看着完全合理。** 这一节比上面的改动更值钱。

- **预算 200 token 测停止率,测出 10%。** 据此写下「瓶颈是复读、根因是预训练
  token 太少」—— 两句都错。我们 SFT 数据答案中位 338 token、平均 374,只有
  20.6% ≤200,天花板就是 20.6%。放到 600 之后是 65%,和探针的 65.0% 精确吻合,
  平均生成 385 ≈ 训练答案平均 374。**量停止率之前必须先看训练答案的长度分布。**
- **「ARC-Easy 赶超 nanochat」。** 它的 ARC 不是似然打分,是渲染成
  Multiple Choice、让模型输出字母。之前纠结它报的是 `acc` 还是 `acc_norm`
  是问错了问题,两个都不是。同一个 S0、同一批题,似然 0.5564、字母 0.2563,
  **差 0.30**。
- **n=20 测停止率。** p≈0.65 时标准误 ±10.7 点,一条 prompt 占 5 点。
  v2 的 65% 和 v3 的 70% 差不到一个标准误,**那不是结论**。

### 特殊 token 的分化只发生在 midtrain

S0 训完 11.8B token 后,`<user>`/`<assistant>`/`<end>`/`<pad>` 的余弦**全是
+1.0000** —— 预训练里出现 0 次,四个是同一个向量。

| | user-assistant | user-end |
|---|---|---|
| S0 | +1.0000 | +1.0000 |
| + midtrain | +0.9625 | +0.9614 |
| + SFT | +0.9627 | +0.9606 |

**SFT 推不动它们 —— 但原因是学习率,不是 mask。** 我原先写「结构性的:
`<assistant>` 落在 prefix 里(mask=0),拿不到输出侧梯度」,那个解释是错的。

「拿不到输出侧梯度」这半句对,但它不是原因:**那些 token 作为输入出现,
后面被监督位置的 loss 依赖它们的表示,梯度会穿过 transformer 回传到嵌入行 ——
输入侧梯度一直存在,mask 不是硬墙。** nanochat 的 mask 和我们完全一样
(`nanochat/tokenizer.py:302-345`:bos / user_start / user_end /
assistant_start 全 0,只有 assistant_end 是 1),它合并成单阶段照样学得会。

实测每个阶段各自移动了多少(嵌入行位移 ÷ 自身范数):

```
          |Δuser|  |Δasst|   |Δend|   普通词中位
S0         0.0000   0.0000   0.0000     0.0000
mid3       0.1780   0.2855   0.2600     0.0663
sft_v3     0.1780   0.2853   0.2605     0.0664   ← SFT 这一跳 ≈ 0.0005
mid4       0.1808   0.2783   0.2791     0.0631
sft_v4     0.1811   0.2779   0.2801     0.0632   ← 同样 ≈ 0.0003
```

**SFT 的位移在第四位小数,midtrain 是 0.18~0.29,差三个数量级。** 而 AdamW 的
lr×步数之比是 1e-4×1573 : 2e-6×396 = **199 倍**,同一个量级。

所以 midtrain 这一段在**当前配方下**不能省;但它不能省的理由是「SFT 的步长
被故意压到 2%」,而那正是 nanochat 两阶段设计的本意。换成它现在的单阶段
(init_lr_frac 0.8)就是另一回事了 —— 见「对齐清单」里那节。

### 位移排名不能用来判断「这个 token 学会了没有」

我曾拿「`<end>` 的位移只排 9921/81903」论证嵌入学习率太低。**那个论证是坏的,
两个方向都错。** 把排名算准之后(mid4 相对 S0,降序):

```
             |Δ|      降序排名             全词表 |Δ| 中位 0.1348
end        0.4398   8367/81903  前 10.2%
assistant  0.4386   8421/81903  前 10.3%
user       0.2850  17819/81903  前 21.8%
<pad>      0.3444  13461/81903  前 16.4%   ← 它在 v4 数据里出现 0 次
```

`<end>` 动得比 **89.8%** 的 token 都多,是中位数的 3.3 倍 —— 不是「比四分之三的
普通词还少」。

而 `<pad>` 那一行才是关键:**它在数据里出现 0 次,位移照样排前 16%。**
原因是 tie —— 嵌入行同时是输出行,softmax 在每个位置都把所有行当负类往下压。
**所以位移大不等于学到了**,这个量根本分不出「学会了」和「被当负类推开了」。

## v3:补中文多选(**外加一个当时没记上的改动**)

> **这一版的归因不干净。** 它同时含了 SFT 学习率 5e-4 → 4e-5,而我当时把下面
> 那 +7.6 点全记在 C3 头上。原因见本节末尾「一个 commit 两个改动」。

`MMLU_AuxTrain` 0.58 → 0.48,让出给 `C3_Train`(CLUE 的 C3,11869 条中文多选
阅读理解,**正经 train split**,和 C-Eval 评测集无重叠)。

起因是实测出来的洞:midtrain 里的多选题全是英文,中文那半(COIG-CQIA)是知乎
长答和考试解析,**一条选择题都没有** —— 于是「看到选项就答字母」只在英文语境
里学会了。

| | v2 | v3 | |
|---|---|---|---|
| 中文格式跟随 | 0.3899 | **0.4657** | +0.076 |
| 英文格式跟随 | 0.9575 | 0.9588 | +0.001,没伤到 ✓ |
| ARC-E(字母) | 0.2647 | 0.2635 | 都是随机 |
| C-Eval(字母) | 0.2419 | 0.2383 | 都是随机 |

**方向对了,幅度不够** —— 但上面这 +7.6 点里有多少是 C3、有多少是 lr,**分不开**。

### 一个 commit 两个改动,而且生效时机不同

`39fad1d`「midtrain 改回连续流打包;SFT 学习率降到 2%」是一次提交两件事。
坑在于**两件事生效的时机不一样**:

```
打包改动   要等下一次 encode 才生效  → v3 的数据 05:00 就编好了,还是 best-fit
lr 改动    要等下一次 SFT 才生效     → v3 的 SFT 06:41 才跑,已经吃到 4e-5
```

于是同一个 commit 的两半落在了**不同的版本**上,而我按 commit 记的账。
对得上账的证据是日志里的 lr:`sft_v3.log` step 20 是 0.000027(warmup 30,
20/30 × 4e-5),`sft_v2.log` 是 0.000333(20/30 × 5e-4);两份数据的被监督
比例也分得开,v3 是 0.9455(best-fit)、v4 是 1.0(连续流)。

**记账要按「哪次跑动吃到了哪个改动」,不是按 commit。** 改数据处理的代码和改
训练超参,前者要重新编码才生效,后者下一次训练就生效 —— 混在一个 commit 里,
提交历史就不再是实验记录了。

规划权重 0.10 实际只拿到 **2.4M token(2.4%)** ——
C3 全量就这么多,抽干了,缺口被 SmolTalk 顶上。对照英文多选占 35.2% 拿到 0.99,
量差 15 倍。按这个斜率外推,要到 0.9 大概需要 15% 的中文多选占比。
下一个候选是 ChID(成语选填,CLUE,train 很大)。

## v4:midtrain 打包改连续流

对照 nanochat 的 `mid_train.py` 和 `chat_sft.py` 逐项核过之后发现两处改错了,
但**只有一处是这一版的改动** —— 另一处(SFT 学习率)已经在 v3 生效了,
见上一节。所以 v4 相对 v3 是**单变量**:打包方式。

**midtrain 不该用 best-fit。** 它只在 SFT 用 best-fit;midtrain 走的是
**预训练那套** —— deque 连续流缓冲、切满、可以切断对话中间、grep 不到任何 mask。
我当时只读了 `chat_sft.py` 就把结论推广了。

```
被监督比例  94.6% → 100.0%      尾部填充  5.4% → 0.0%
```

步数不变(1573 × 16 × 4 = 100,672 行),但两版**喂进去的被监督 token 不一样**:

```
v3   103,115 行可用,走 0.976 epoch   100,672 × 1024 × 0.9455 =  97.5M
v4    97,511 行可用,走 1.032 epoch   100,672 × 1024 × 1.0    = 103.1M   +5.75%
```

v4 还重复了自己 3.2% 的数据,v3 没走完一个 epoch,这也是个不对称。

### 结果:loss 说没进步,行为说进步很大

同一批 prompt(n=200,中英各半)、同一套判据重测两版:

| | v3(best-fit) | v4(连续流) | |
|---|---|---|---|
| 停止率 合计 | 43.0% ±3.5 | **67.0% ±3.3** | +24 点 |
| 停止率 en | 57% | 65% | +8(一个多标准误) |
| 停止率 **zh** | 29% | **69%** | **+40 点** |
| 格式跟随 zh | 0.4657 | **0.7834** | +31.7(n=277,12 个标准误) |
| 格式跟随 en | 0.9588 | 0.9592 | 没动 |
| ARC-E(字母) | 0.2635 | 0.2597 | 都是随机 |
| C-Eval(字母) | 0.2383 | 0.2094 | 都是随机 |

而 loss 那一侧,**3 模型 × 2 数据**的隔离格子(每份抽 512 行,按 sum/有效
token 汇总):

```
        v3 数据    v4 数据      差
S0      2.6746    2.2667    -0.4080   ← 纯数据难度,S0 两边都没训过
mid3    2.0265    1.7519
mid4    2.0820    1.7070

训练质量(mid4 − mid3):  v3 数据上 +0.0554     v4 数据上 -0.0450
```

**v4 的数据本身就容易 0.41**,比观测到的训练 loss 差(约 -0.30)还大 ——
所以那 -0.30 全部由数据难度解释,**v4 在 loss 上不是改进**。在同一份数据上比
两个模型,各自在自己的主场赢,**没有一致的胜者**。

> **这是这一版最该记住的东西:后训练阶段 loss 不是好裁判。** 连续流打包没让
> 模型更会预测文本,是让它更会收尾、更会听指令 —— 两个行为指标在中文侧各涨
> 40 和 32 点,而 loss 判据会把这一版判成平手。
>
> 直接后果:下面「加验证集」那条,我原先标成**最高优先级缺口,那是错的**。
> val loss 抓不到 v4 这种改进。它防的是另一类问题(训崩了、过拟合了),
> 不能拿它当后训练的主判据。

旧的 n=20 判据顺带被证伪了一次:v3 在那 20 条上是 70%,在新集上是 43%。

### 为什么只在中文侧?机制还没定

两版的 `actual_tokens` **逐源完全相同**(SmolTalk 47.5M / COIG-CQIA 13.5M /
MMLU-Aux 35.2M / C3 2.4M / GSM8K 1.2M),C3 的行数也几乎一样(best-fit 约
2371 行 vs 连续流 2342 行)。所以增益不可能来自「中文数据变多了」。

**证伪过的解释,记下来省得再想一遍:**

- ~~best-fit 把塞不进的对话截断,丢掉了末尾的答案字母~~ ——
  读 `chat.py:403` 的 `pack()`:它**从不截断**,一条对话要么整条装进某行,
  要么留在池子里等下一行。两版含的对话内容完全一致。
- ~~中文格式跟随处在陡峭区,任何扰动都推很多~~ —— 两个**互相独立**的指标
  (停止率、格式跟随)在中文侧同时大跳,同时处在陡峭区太巧了。
- ~~v4 多喂了 5.75% 监督 token~~ —— 5.75% 换 40 点,量级完全不成比例。

- ~~那 5.45% 的 padding 集中在中文源上(COIG-CQIA 对话长,best-fit 按长度降序
  装箱,一条 900 token 的中文对话只能补 124 个 pad)~~ —— **量了,反方向**:

  ```
  v3   zh: 占 15.0% 的 token | 行内 pad 3.92% | 占全部 pad 的 10.3%
       en: 占 85.0% 的 token | 行内 pad 6.03% | 占全部 pad 的 89.7%
  ```

  中文行的 pad 比例比英文**低**,中文只吃掉全部 padding 的 10.3%。
  best-fit 的浪费不但没专砸中文,还略偏英文。

**机制目前不知道。** 四个解释都被自己的测量推翻了,这一条留着不填 ——
「打包改连续流会让中文行为大幅变好」现在是个**可复现但无解释**的事实。

已知的相关事实,给下一个想解释它的人:midtrain 里中文只占 **15%** 的 token
(COIG-CQIA 13.5M + C3 2.4M),`<bos>` 密度两版几乎相同(v3 每行 2.28、
v4 2.43),两版逐源 token 数完全一致。

**在解释清楚之前,不要把「连续流」当成一个可以到处套的结论** —— 尤其
SFT 那一侧仍然在用 best-fit,而我们并不知道该不该一起改。

## 还差什么:对齐清单

### 先说一件影响路线的事:nanochat 上游已经不做两阶段了

`1ddaad1`(2026-01-31)commit message 是「nuke midtraining from orbit,
it's not as needed now that we have a BOS-aligned dataloader」。但**不是删掉,
是合并** —— 新 `chat_sft.py` 的混比就是旧 `mid_train.py` 的混比(SmolTalk 460K
+ 身份对话 ×2 + MMLU-aux ×3 + GSM8K ×4 + 拼写 200K/80K),`mid_train.py` 少了
386 行,`chat_sft.py` 多了约 300 行。

关键是学习率跟着改了:

```
旧(两阶段)   midtrain init_lr_frac 1.0  →  SFT init_lr_frac 0.02   差 50 倍
新(单阶段)   一个 SFT,init_lr_frac 0.8   (embedding_lr 也从 0.2 提到 0.3)
```

**旧版那个 0.02 只在「前面有个全速 midtrain 打好底」的前提下成立。**

对我们的三点含义:

1. **不用改现在的路线。** 我们对照的 d20 产于这次重构之前(`aa530cd^` 里
   `mid_train.py` 还在),它就是两阶段训出来的 —— 95% 那个对照和我们的
   midtrain → SFT 同类可比,A 组把 SFT 定在 2% 也是对的。
2. **C 组里「预训练每行以 BOS 开头」价值被我低估了。** 上游认为它足以顶掉
   整个 midtrain 阶段(`43c29dd`「Big DataLoader refactor: BOS-aligned
   dataloaders」)。重做预训练时这是便宜且影响大的一项。
3. **但我们有个量到过的理由不能照着合并**:特殊 token 的余弦从 1.0000 分化到
   0.9625 **只发生在 midtrain**,SFT 推不动(`<assistant>` 落在 mask=0 的
   prefix 里,拿不到输出侧梯度)。要合并就必须同时把 lr 提到 0.8 那个量级,
   照旧版的 2% 合并等于特殊 token 永远学不会。

它还顺带加了真正的验证集:`SmolTalk(split="test")` + `MMLU(split="test")`,
是**held-out split**,比我们「留出打包后的尾部行」干净 —— 我们那个尾部行和
训练行同源同分布,只能防训崩,防不了「配方选错了」。

### A 组 —— 纯配置(已实现,v5 在验)

| | nanochat | 我们 |
|---|---|---|
| midtrain lr 调度 | 前 80% **不衰减**,后 20% 线性到 **0** | cosine + warmup 50 + 底 0.1 |
| SFT lr 调度 | 线性 1.0 → **0** | cosine + 底 0.1 |
| Muon momentum | 前 300 步 **0.85 → 0.95** 预热 | 固定 0.95 |
| AdamW betas | **(0.8, 0.95)** | (0.9, 0.95) |
| AdamW 的 wd | **硬编码 0**,wd 只给 Muon | 两者共用一个 wd |
| AdamW lr 的 1/√d 缩放 | lr **× (d/768)^-0.5** | 无(我们该乘 0.866) |

前两项**不用改代码**,现成的调度就能表达它的形状:

```
midtrain   --lr_schedule wsd --lr_decay_steps <20% 步数> --min_lr_ratio 0 --warmup_steps 0
SFT        --lr_schedule linear --min_lr_ratio 0 --warmup_steps 0
```

后四项要动 `src/train.py`,但**都加成带默认值的开关,不改现有默认** ——
那几个值(betas、wd 的分组、动量)预训练和 ReTok 两条线也在用,而那两条线
已经发布了权重。直接改硬编码等于悄悄换掉它们的配方,**而且不会报错**。

### 对齐的基准:Summer = nanochat + 中文 + ReTok,架构固定 Qwen3

这条定下来之后,**偏离才需要理由**,不是对齐需要理由。同时它把架构类的对齐项
**关闭**,不是推迟:

| | 结论 |
|---|---|
| `tie_word_embeddings=True` | **保留** —— 这是 Qwen3-0.6B-Base 的配置。于是下面 B 组不再是目标 |
| RMSNorm 带可学权重 | **保留** —— Qwen3 自带 |
| `resid_lambdas` / `ve_gate` 之类 | 不引入 |

剩下的对齐面就三块:**数据与任务、配方与超参、代码组织**。

### B 组 —— 已关闭(架构固定 Qwen3)

```
                nanochat(d20 实际值)      我们      倍数
Muon(矩阵)     0.02                    2e-3      10×
embedding      0.2 × 0.775 = 0.155     1e-4    1550×
unembedding    0.004 × 0.775 = 0.0031  1e-4      31×
```

它把嵌入和输出头分成**两个独立参数组**,嵌入的学习率比矩阵还高 8 倍。我们
`tie_word_embeddings=True`,两者是同一个张量,只能给一个学习率。

**这一组的证据被我自己推翻了一半,优先级要降。** 我原来的论证是「`<end>` 的
位移只排 9921/81903,说明它动得太少」—— 排名算准之后是**前 10.2%**,动得比
89.8% 的 token 都多;而且 `<pad>` 在数据里出现 0 次也排前 16%,因为 tie 让
softmax 把所有行当负类压。**位移排名分不出「学会了」和「被推开了」**,拿它
论证嵌入学习率不成立。见「位移排名不能用来判断…」那节。

留下来的仍然是真差异 —— 1550 倍不是小数字,而且它把嵌入和输出头绑在一个学习率
上,**这本身就限制了能表达的配方**(比如上游单阶段那套 embedding_lr 0.3 +
unembedding_lr 0.004,我们根本写不出来)。但「它是当前某个具体问题的根因」这句
现在没有证据。

**解 tie 需要重做预训练,而架构固定 Qwen3 就意味着不解。** 所以这一组不做了 ——
代价是写不出上游那种 embedding/unembedding 分开的配方,认了。

### C 组 —— 数据与配方(架构项已剔除)

对齐目标是**两阶段**那一版(`aa530cd^`),不是上游现在合并后的单阶段:

```
midtrain  848K 行   SmolTalk 460K + MMLU-aux 100K + GSM8K 8K + 身份对话×2
                    + SimpleSpelling 200K + SpellingBee 80K
SFT        23K 行   ARC-E 2.3K + ARC-C 1.1K + GSM8K 8K + SmolTalk(前 10K)
                    + 身份对话 1K + 拼写 300+300
验证集              两阶段都用 test split
```

| | 差异 |
|---|---|
| 混比的单位 | 它按**行数 / epoch**(重复一次就是多一个 epoch),我们按 token 权重 |
| SFT 数据 | 它有 ARC train 3.4K + GSM8K 8K + 身份对话 1K + 拼写 0.6K,我们只有 SmolTalk + COIG-CQIA |
| midtrain 数据 | 同上多两类;SmolTalk 用**全量 460K**,我们用子集 |
| batch | 它 midtrain 每步 **524288** token,我们 65536,小 8 倍 |
| seq_len | 2048 vs 我们 1024 |
| `<user_end>` | 它有,我们没有 —— 加要重建词表,会破坏所有已发布模型 |

**逐条照搬会删掉中文。** 它是纯英文的,照搬等于把 COIG-CQIA 和 C3 去掉。
所以对齐的是**结构**:混比按行数算、任务类型补齐,中文侧配对应的源。
| 预训练每行以 BOS 开头 | 它保证,我们不保证。**上游认为这一项足以顶掉整个 midtrain 阶段**,见上面那节 |
| 两阶段 vs 单阶段 | 它现在是一个 SFT(init_lr_frac 0.8),我们是 midtrain(1.0)+ SFT(0.02) |
| 验证集 | 它用 SmolTalk / MMLU 的 **test split**,我们只能留出同分布的尾部行 |

### BOS 对齐的三个代价(预演实测,规划时要算进去)

BOS + best-fit 是设计 B 的核心,但它不是免费的。depth-10 预演跑满 310M token
之后量到三件事:

**1. 丢弃 48%,语料需求翻倍。**

```
Gutenberg        84.0%   ← 整本书,一行 1025 装不下,反复裁
CN_FineWeb_Edu   50.1%      Wikipedia_EN   37.3%      CC_CN      28.4%
Wikipedia_CN     42.0%      FineWebEdu     35.5%      SkyPile    26.6%
CCI3-HQ          41.5%      CC_EN          29.1%      Cosmopedia 26.0%
合计 48.0%(400M / 834M)
```

FineWebEdu 的 35.5% 和 nanochat 自述的 35% 精确吻合(那是它的主要语料),
所以实现是忠实的;**我们整体更高,因为语料里有长文档源**。
**现有 9.9B 的池子在这套打包下只出得到约 5B** —— 规划按 2 倍算,不然差一倍。

**2. Gutenberg 基本报废。** 84% 白扔,3% 的权重实际只有 0.5% 进得去。
连续流打包下书是一个 token 都不浪费的(切成很多行),**这是 BOS 对齐新引入的
代价**。要么去掉,要么先按章节切分再编码。nanochat 语料里没有书,没这个问题。

**3. 小样本会把丢弃率严重低估。** 我第一次用 20M token 量出 3.2%~17%,
据此写下「我们浪费得比它少,是好消息」—— 错的。best-fit **优先消费装得下的
短文档,长文档在缓冲区里堆积**;跑动提早结束时那批还没被裁,分母算了、分子没算。

### 小模型不按参数比例变快

depth-10(114M)对 0.5B(524M)参数少 4.6 倍,但实测**只快约 2 倍**
(每 50 步 215 秒,GPU 100%、显存 21.7GB)。batch 16 × seq 1025 的激活值仍然
占主导,参数少省不下多少。**预演的加速比按 2 倍算,不是 4 倍。**

顺带一处我说错过的:`--dmodel_lr_scale` 是 `(d_model/768)^-0.5`,我一直说
「该乘 0.866」—— 那只对 d=1024 成立。d=640 时是 **×1.0954,放大而不是缩小**。
它是 d 的函数,不是常数。

### 判据层面的缺口

**我们整条 midtrain/SFT 没有验证集。** nanochat 每 150 步测一次 val bpb 并
记最优;我们只取最后一步,全靠事后评测。

> **但它不是最高优先级** —— 我一度这么标,v4 的结果直接反驳了:val loss
> 会把 v4 判成平手(数据难度解释了全部 loss 差,同一数据上各赢自己主场),
> 而它是目前效果最大的一版。**val loss 防的是训崩和过拟合,不是后训练的主判据。**
> 主判据得是行为侧的:停止率、格式跟随,而且要够大的 n。

做法不用重新编码:`prepare/chat.py` 是**全局 shuffle 之后才写盘**的(第 482
行),所以留出尾部 N 行天然跨数据源分层,在 `train.py` 的 `epoch_order` 里把
`len(dataset)` 换成 `n_train = len(dataset) - val_rows` 即可。

**但这个验证集只对之后的跑动有意义** —— 尾部那些行 mid3 / mid4 都已经训过了,
拿它去回头量现有 checkpoint 是自欺欺人。

### 训练 loss 不能跨版本比(已验证)

`midtrain4` 的 loss 比 `midtrain3` 低约 0.30。**实测这 0.30 全是数据难度** ——
S0 在两份数据上就差 0.4080,比那 0.30 还大。格子和读数在 v4 那节。

隔离办法记在这儿:**3 模型 × 2 数据**。同一个 S0 在两份数据上算 loss,差值
就是纯数据难度;再在**同一份数据**上比两个模型,而且要看两个方向 —— 每个模型
都在自己那份数据上训过、各占主场,**只有两边都赢才算真赢**(v4 没有:
+0.0554 / -0.0450)。

口径上两个坑:按 **sum / 有效 token 总数**汇总,不能先算每 batch 的均值再平均
(两版被监督比例不同,会给短行更大权重);两份数据用**同一批行下标**配对。

## 附:怎么加载 nanochat 的 d20 做对照

官方 chatsft 权重是干净的(122 张量 / 560.99M),卡住的是**代码版本**:仓库
HEAD 已是新架构,多出 `resid_lambdas` 等 25 个键。做法:

```bash
git fetch --unshallow                       # 默认是 depth 1
git worktree add ../repo_old $(git rev-parse aa530cd^)   # 退到引入那次的父提交
```

然后 `load_state_dict(strict=True)` 全键匹配。`rustbpe` 只是训练器,推理走
tiktoken,顶层 import 用空壳模块绕过即可。

**社区移植版(HarleyCooper/nanochat561)没去修**:它自带的 tokenizer.pkl 是坏的
(n_vocab 报 141260,模型是 65536),换官方 pkl 之后 `modeling_nanochat.py` 又在
`apply_rotary_emb` 挂掉(cos/sin 按 (B,H,T,D) 构造,qkv 是 (B,T,H,D))。
手补一个移植版的布局 bug,补错了模型就输出垃圾,**而垃圾永远不会停** ——
会得到一个看起来像结果的假低停止率。

协议实现要**先在已知答案上校验**:拿 d20 跑我们的 `mc_eval.py` 打分逻辑得
0.3994,它 meta 里是 0.4033,差 -0.0039,才敢用。

### 渲染格式的落差有 0.88,比任何配方改动都大

```
                render=nanochat   render=ours
arc_easy 格式      0.9592          0.5210
ceval    格式      1.0000          0.1227     ← 同一个模型,差 0.88

### 中文停止率 4%:是我的配方错误

```
en  61.0%   平均生成 420
zh   4.0%   平均生成 583   ← 几乎全烧到 600 的预算上限
```

格式跟随 1.0 而停止率 4% 不矛盾:前者只看一个 token,后者要求在长答案之后吐出
`<end>`。所以问题定位在**中文语境下的 `<end>`**。

`<end>` 是**按条**出现的,所以要看条数占比,不是 token 占比:

```
SimpleSpelling  200,000  33.7%  en        COIG_CQIA   33,700   5.7%  zh
SmolTalk        136,749  23.0%  en        GSM8K       29,892   5.0%  en
MMLU_AuxTrain    99,669  16.8%  en        C3_Train    11,856   2.0%  zh
SpellingBee       80,000  13.5%  en

中文 45,556 = 7.7%   |   英文拼写 280,000 = **47.1%**
```

**照抄了 nanochat 的拼写量(200K+80K),但它总量 848K、纯英文;我们把 SmolTalk
截到 10 万之后总量只有 59 万,拼写的相对权重从 33% 涨到 47%。**
模型学到的 `<end>` 分布几乎全是「短英文答案之后」。

> 截 SmolTalk 时我只算了 **token 占比**(中文 6%),没算**条数占比** ——
> 而 `<end>` 这类「每条一次」的信号只受条数支配。**改混比时两种占比都要算。**

**这个缺陷是尺度无关的,0.5B 上照跑会重现。** 但那个 4% 本身不能推到 0.5B ——
模型小 4.6 倍、预训练只有 300M、单阶段 vs 两阶段、掩码不同,变量太多。

### 顺带暴露的两个工程问题

- **主判据脚本住在 `/tmp`**,机器硬复位后被清空,而链路里的 `2>/dev/null`
  把「文件不存在」吞掉了 —— **静默失败**。已搬进 `prepare/stoprate.py`。
- **预演链路原来不能续跑**,六个阶段串在一起,断在 step 850/1150 就整条重来。
  现已改成每步幂等(产物在就跳过,训练自动从最新 checkpoint 续),
  **重跑脚本 = 自动续跑**。找 checkpoint 用数字排序 —— 字典序会选中
  `checkpoint-500` 而不是 `1000`,从更早的点续训**而且不报错**。

### 验证:中文条数占比就是 `<end>` 的杠杆

只改一处 —— 中文两个源各从 1 个 epoch 变成 4 个(条数占比 7.7% → 24.9%),
英文条数、超参、预训练底座全部不动。**今天少有的干净单变量。**

| | 中文 7.7% | 中文 24.9% | 判断 |
|---|---|---|---|
| 停止率 **zh** | 4.0% | **31.0%** | +27 点 = **5.4 个差值标准误** ✓ |
| 停止率 en | 61.0% | 71.0% | +10 点,没掉(反而升)✓ |
| 停止率 合计 | 32.5% ±3.3 | 51.0% ±3.5 | |
| 格式跟随 zh(nanochat) | 1.0000 | 1.0000 | 没掉 ✓ |
| 格式跟随 en(nanochat) | 0.9592 | 0.9592 | 完全一致 |
| arc_easy acc | 0.2963 | 0.3013 | 噪声 |
| ceval acc | 0.2744 | 0.3105 | 噪声内;但比随机线高 2.2 SE |

**结论:`<end>` 的行为由监督阶段的条数占比决定。** 这也是「改混比时 token 占比
和条数占比都要算」那条通则的实证。

副产物:`ours` 渲染下的格式跟随**进一步崩塌**(arc_easy 0.5210 → 0.2639,
ceval 0.1227 → 0.0758)。多训一倍 nanochat 渲染的数据,模型就更专一于那个格式
—— 说明**渲染效应是「学到的格式」而不是「能力」**。

三条边界,别把结论说过头:

1. **中文 31% 离英文 71% 还很远。** 杠杆有效但没拉平。剩下的差距要靠更多
   **唯一**的中文数据(COIG 只有 44.7K 条,还因超 seq 丢 24.6%)—— ×4 已经在冒
   过拟合的风险,再加 epoch 不是办法。
2. **绝对数字不能推到 0.5B**(114M / 只训 300M token)。能推的是杠杆方向。
3. **这和 v3→v4 那个未解的打包之谜是两回事** —— v3/v4 用的是同一份 sft3
   (中文按条数超 50%),所以那次的 +40 点不是这个原因。两个都是数据构成效应,
   这反而强化同一个判断:**数据构成的量级远大于超参**(对照 v5 的 A 组六项,
   全部落在噪声内)。

### 三版预演的横向对照:停止率是零和的

同一个预训练底座(`summer114m_base`)、同一套超参,**只改后训练数据的中文占比**:

| | zh7 | zh25 | zh49 | |
|---|---|---|---|---|
| 中文条数占比 | 7.7% | 24.9% | 49.1% | |
| 中文来源 | COIG ×1 | COIG/C3 **各 ×4** | 四源,**全唯一** | |
| 停止率 **zh** | 4% | 31% | 47% | 25→49 时 +16 = 2.4 SE |
| 停止率 **en** | 61% | 71% | **52%** | 25→49 时 **−19 = 2.8 SE** |
| 停止率 合计 | 32.5% | **51.0%** | 49.5% | **总量没动**(差值 SE 4.9) |
| 格式跟随 zh | 1.0000 | 1.0000 | 1.0000 | C3 从 6.5% 稀释到 1.1% 也没掉 |
| 格式跟随 en | 0.9592 | 0.9592 | 0.9592 | 三次完全一致 |
| ceval acc | 0.2744 | 0.3105 | 0.3141 | |
| arc_easy acc | 0.2963 | 0.3013 | 0.2908 | 随机线 0.25 |

**总的停止能力是固定的,条数占比只决定它怎么在两种语言之间分配。**
中文多拿 16 点,英文就少 19 点,总量 51.0% → 49.5% 没变。

所以 v6 定在**中文 30%** 而不是 50% —— zh25 是三版里总量最好的,英文还保住 71%。

> **边界:零和可能是 114M 的容量假象。** 它嵌入占 46%、只训了 300M token,
> 总停止能力才 50%;0.5B 的 v5 总量是 71.5%,容量宽得多。
> **只取方向,不拿 114M 的曲线去精调 0.5B 的比例。**

一个有价值的否定结果:**C3 的占比不是中文选择题格式的驱动因素**。它从 6.5%
稀释到 1.1%,中文格式跟随三版都是 1.0000 —— 要么通用中文指令数据就够,
要么这个格式从英文 MMLU 迁移过来了。省下的中文多选配额可以给别的。

## v6:0.5B 单阶段 —— 在 d20 的判据上超过它,但**不是干净的胜利**

从 S0 起,设计 B 单阶段(best-fit + assistant-only,lr = 预训练的 0.8),
新混比(中文 29.8%、MMLU ×3、补回 ARC train),346M token / 5280 步 / 4.8 小时。

### 结果

| | v6 | nanochat d20 | |
|---|---|---|---|
| **arc_easy** | **0.4865** | 0.4033 | **+0.083** |
| **mmlu** | **0.3353** | 0.3232 | **+0.012** |
| arc_challenge | 0.3549 | — | |
| ceval | 0.3574 | — | 中文,它没有 |
| 英文格式跟随 | 0.9996 | 0.9996 | 完全一致 |
| 中文格式跟随 | 1.0000 | — | |
| 停止率 合计 | 54.5% | **95%** | 主要剩余差距 |

判据是同一套字母 MC 协议(实现在 d20 上校验过:我们跑出 0.3994,它 meta 里
0.4033,差 -0.0039)。

### 但两个胜负都被污染了 —— 自己说清楚

```
d20 的 midtrain   MMLU auxiliary_train ×1  (100K 条)
v6                MMLU auxiliary_train ×3  (300K 条)
```

而 MMLU-aux 的原始来源是「ARC / MC_TEST / OBQA / RACE」——
**它不只帮 MMLU,也直接帮 ARC。所以 arc_easy 那 +0.083 也不干净。**

ARC train 那一项是公平的(双方都 ×1,而且 train / test 不重叠)。

**要拿干净的结论,必须用 MMLU ×1 重跑一次。** 这是开跑前就预先声明的归因拆分
—— v6 把「换渲染」和「补 ARC/MMLU」打包在一起了,和本文批评过的做法一样,
区别只在于这次是**有意为之并提前标注**:先确认能不能过线,过了再拆。

### 代价:中文停止率崩了,而且预演精确预言过

| | v5 | v6 | |
|---|---|---|---|
| 停止率 en | 70% | 72% | 持平 |
| 停止率 **zh** | 73% | **37%** | **−36 点** |
| 停止率 合计 | 71.5% | 54.5% | −17 点 |

v5 的最后监督阶段(sft3)中文按条数超过 50% → zh 73%;v6 是 29.8% → zh 37%。
而 **114M 预演在中文 24.9% 时给出 zh 31%** —— 同一条曲线,跨了 4.6 倍的模型规模。

> **这条的价值可能比 v6 本身还大:114M 的预演能定量预测 0.5B 的行为。**
> 预演从「省时间的权宜之计」变成了可信的筛选手段。

`ours` 渲染那一列全面崩塌(arc_easy 格式 0.9996 → 0.3556),再次说明**渲染效应
是学到的格式而不是能力**,训练和评测必须用同一份。

## v7:MMLU ×1 的对照 —— 干净的结论,以及停止率的杠杆

和 v6 **逐项相同,只把 MMLU auxiliary_train 从 ×3 改回 ×1**(= d20 的 midtrain)。

| | v6(×3) | **v7(×1)** | d20 | |
|---|---|---|---|---|
| arc_easy | 0.4865 | **0.4306** | 0.4033 | **+0.027 = 2.7 SE,真实超过** |
| mmlu | 0.3353 | 0.3242 | 0.3232 | +0.001 = 0.25 SE,**平手** |
| arc_challenge | 0.3549 | 0.3217 | — | |
| ceval | 0.3574 | 0.3321 | — | |
| 停止率 合计 | 54.5% | **67.5%** | 95% | |
| 停止率 en | 72% | 78% | | |
| 停止率 zh | 37% | 57% | | |

### 对 d20 的干净结论

**ARC-Easy 真实超过**(n=2376,SE 1.0 点);**MMLU 是平手**(n=14042,SE 0.4 点,
差 0.1 点)。比 v6 那个带星号的「+0.083 / +0.012」诚实得多 —— 那两个数里有
MMLU-aux ×3 的成分,而 MMLU-aux 的来源正是 ARC / MC_TEST / OBQA / RACE。

### MMLU ×3 买到了什么:accuracy,代价是停止率

```
MMLU ×1 → ×3    arc_easy +5.6 点   mmlu +1.1 点   停止率 −13 点
```

**它不是浪费。** v7 训到一半时我看 val loss 已经追平 v6(1.2686 vs 1.2688),
一度怀疑 ×3 纯属烧算力 —— **又一次错在拿 val loss 当判据**。

### 找到了抬「总量」的杠杆:少放超短答案的任务

停止率 54.5% → 67.5%,**英文和中文同时涨**(72→78,37→57)。这是总量在涨,
不是分配在变 —— 而在此之前测到的所有杠杆(中文条数占比)都是**零和**的。

归因里有一处混淆,说清楚:去掉 20 万条 MMLU 同时做了两件事 ——
减少超短答案,**以及把中文条数占比从 29.8% 抬到 36.6%**(分母变小)。
按已知的零和曲线,36.6% 大约对应 zh 40%,而实测 57%,
**所以多出来的约 17 点来自「超短答案变少」**;英文那 +6 点也只能这么解释
(英文条数占比反而降了)。

机制上讲得通:MMLU 是「长题面 + 一个字母答案」,`<end>` 全部出现在一个 token
之后。它占 28% 条数时,模型学到的「答多长该收尾」被带偏,开放问答时就不知道
在哪停。

> **通则:`<end>` 的行为由两个量决定 —— 条数占比(决定语言间的分配,零和)
> 和答案长度分布(决定总量,非零和)。** 之前只找到第一个。

### 停止率的差距是真的 —— 先验判据,再追

我一直拿「nanochat d20 停止率 95%」当追赶目标,但那是在**旧的 20 条手写英文
prompt** 上量的(n=20,SE ±10.7),而我们现在报的是新的 200 条(中英各半)。
**两套 prompt 集不同,不可比** —— 这条我自己写进过 `prepare/stoprate.py`,
却一直拿 95% 当靶子。而且 200 条里有 100 条中文,**nanochat 不会中文**。

所以先把判据本身验一遍:拿 **nanochat 自己的模型**跑**我们那 100 条英文 prompt**。
d20 的权重本地已经没有了,用本地的 **d12**(vocab 32768 / 12L / 768H,
新版代码单阶段训的,比我们的 524M 小得多):

```
nanochat d12  [en] 94.0% ±2.4   平均生成 239 token
我们 v7       [en] 78.0% ±4.1   平均生成 342 token
差 16 点 = 3.3 个差值标准误
```

**结论:95% 稳健,差距是真的。** 我怀疑判据不可比 —— 怀疑错了。
而且这还是个更小的模型。

### 由此改判:BOS 对齐从「可以推迟」变成头号嫌疑

一小时前我判断「BOS 对齐收益没量过、代价 48% 语料,预训练重做可以无限期推迟」。
代价那半仍然成立,但**「没量过」现在有了具体的怀疑对象**:

```
                d12                我们 S0
预训练打包    BOS + best-fit       连续流
每行开头      永远是文档边界        任意位置(可能在文档中间)
seq           2048                 1024
```

BOS 对齐下模型每一行都看到「文档从这里开始、到那里结束」的完整结构;
连续流下看到的是被任意切断的片段。**「什么时候该结束」这个信号,
在 BOS 对齐下干净得多** —— 而停止率正是这个能力。

**验法**(约半天):现有的 `summer114m_base` 是 BOS 对齐的,再训一个连续流版本
(depth-10 / 300M token),两个底座各跑同样的单阶段后训练,比停止率。
预演已经证明能定量预测 0.5B(中文条数占比那条曲线,四个点跨 4.6 倍规模)。
